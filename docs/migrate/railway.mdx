---
title: "Migrate from Railway"
description: "Move a Railway project, its variables, Postgres, and volumes onto InstaCloud."
---

Railway and InstaCloud think about deployments the same way, so the concepts map almost one to one. A Railway service becomes a **compute** service, Railway Postgres becomes a **postgres** service, and variables become project secrets that you bind into the app. The export is the fiddly part, because Railway has no command that dumps a whole project. You walk it one service at a time.

## TL;DR

```bash
npx -y insta@latest setup agent --create
insta services add compute app
insta services add postgres db
insta secrets bind DATABASE_URL postgres/db --to compute/app
insta compute connect-repo <owner/repo> app
insta compute set-domain <your-domain> --group app
```

<Steps>
  <Step title="1. Inventory the Railway project" titleSize="h2">
    Link the project, then target each service in turn.

    ```bash
    railway link                 # pick the project and environment
    railway service              # pick the service you are migrating
    railway variable list        # its variables
    railway status --json        # services, volumes and buckets
    ```

    `railway status` only reports services with a live deployment, so a stopped Postgres looks the same as one that was never created. Run `railway deployment list` per service before you decide a database is unused.

    <Warning>
      `railway variable list` prints resolved values, so a reference like `${{Postgres.DATABASE_URL}}` comes out as a real connection string pointing at Railway's Postgres. Copying that across leaves your migrated app talking to the database you are trying to leave. Skip every connection string you are binding below.
    </Warning>
  </Step>

  <Step title="2. Create the project and services" titleSize="h2">
    ```bash
    npx -y insta@latest setup agent --create
    insta services add compute app
    insta services add postgres db      # plus redis/mysql/mongodb/storage to match
    ```

    One compute service per Railway service.
  </Step>

  <Step title="3. Bind the database and deploy" titleSize="h2">
    Bind the credentials your app needs, then point InstaCloud at your repo.

    ```bash
    insta secrets bind DATABASE_URL postgres/db --to compute/app
    insta compute connect-repo <owner/repo> app
    ```

    `connect-repo` builds on the server and detects your runtime with nixpacks, the same job Railpack was doing, so you do not need a Dockerfile. Add `--root-dir` for a monorepo. If you already publish an image, use `insta deploy --image <ref> --port <n>` instead.

    Then copy the remaining variables. Skip `RAILWAY_*` and `PORT`, which the platform supplies, and skip anything you bound above.

    ```bash
    insta secrets set <NAME>            # value read from stdin
    ```
  </Step>

  <Step title="4. Move the data" titleSize="h2">
    Railway has no maintenance mode, so scale the service to zero in the dashboard, and do the same for every worker and cron service, so nothing is still writing.

    ```bash
    pg_dump --no-owner --no-privileges "$RAILWAY_DATABASE_URL" \
      | grep -v -E '^SET transaction_timeout' \
      | psql -v ON_ERROR_STOP=1 "$(insta db url --group db)"
    ```

    The `grep` drops one setting that Railway's Postgres writes and InstaCloud's does not recognise. Then compare a few row counts before you carry on.

    ```bash
    psql "$(insta db url --group db)" -c \
      "select relname, n_live_tup from pg_stat_user_tables order by n_live_tup desc limit 5"
    ```
  </Step>

  <Step title="5. Move a volume, if you have one" titleSize="h2">
    A new InstaCloud volume is empty, and nothing is copied for you. Download the files while the Railway service is still running, because Railway cannot read a volume whose service is stopped.

    ```bash
    railway volume files download /path/to/file ./local-copy
    insta compute volume app --size 10    # attach a /data disk
    insta compute restart app             # the disk mounts on the next deploy
    ```

    The disk mounts at `/data` on the deploy after you attach it, so redeploy before you write to it. Copy the files in through your app, or with `insta compute exec app -- <cmd>`.
  </Step>

  <Step title="6. Restart, then move the domain" titleSize="h2">
    A restart re-resolves the environment, so the app picks up its new database.

    ```bash
    insta compute restart app
    insta compute set-domain <your-domain> --group app
    insta compute check-domain <your-domain> --group app
    ```

    `set-domain` returns the DNS records to publish at your provider. Publish them, then run `check-domain` again. Keep Railway frozen until the old records age out.

    <Warning>
      If you stopped the InstaCloud service at any point, `insta compute start` on its own brings the machine back with its old environment, and the app keeps writing to the old database. Run `restart` after `start`.
    </Warning>
  </Step>
</Steps>

## Workers and cron services

A Railway worker becomes a second compute service. Give it a port to listen on, and leave always-on enabled, because a suspended worker has no traffic to wake it.

Railway cron services have no direct equivalent. Use `pg_cron`, which InstaCloud's Postgres ships, or run a scheduler inside an always-on service.
