Railway and InstaCloud think about deployments the same way, so the concepts map almost one to one. This guide takes you from a running Railway project to the same app on InstaCloud, with its data. You will spend most of it telling your coding agent what to do.

InstaCloud offers:

- **Postgres with real branching.** Give a feature, or an agent task, its own database and its own compute, then merge the structure back.
- **Built for coding agents.** A CLI and an MCP server your agent drives directly, with an approval gate on the actions that matter.
- **Flexible deployments.** A GitHub repo with no Dockerfile needed, your own Dockerfile, or an image from any registry.
- **Managed services alongside.** Postgres, Redis, MySQL, MongoDB, and object storage in one project.
- **Real support.** An active community on [Discord](https://discord.com/invite/MPxwj5xVvW).

## Migration steps

Here is how the two platforms line up:

| On Railway | On InstaCloud |
|---|---|
| Service | **compute** service |
| Railway Postgres | **postgres** service |
| Variables | project secrets |
| `${{Postgres.DATABASE_URL}}` reference | a binding from the postgres service |
| Volume | `insta compute volume`, mounted at `/data` |
| Cron service | `pg_cron`, or a scheduler in an always-on service |

### 1. Set up your coding agent

```bash
npx -y insta@latest setup agent --create
```

That installs the `insta` CLI, creates a project, links this directory to it, and registers the `insta` skill with every coding agent on this machine. The skill is what carries the migration runbook.

You can also create the project in the [console](https://console.instacloud.com) and connect an agent from its Quick Start page.

{/* screenshot: console, project Quick Start page with the connect-agent one-liner */}

### 2. Do the parts only you can

Railway has no command that dumps a whole project, and its CLI picks a project and service interactively, so start it yourself:

```bash
railway link          # pick the project and environment
railway status --json # services, volumes and buckets
```

Two more things your agent cannot reach: **your DNS provider login**, for the last step, and **a volume's contents** if you have one. Railway refuses to read a volume whose service is stopped, so download the files before anything gets scaled down.

```bash
railway volume files download /path/to/file ./local-copy
```

### 3. Ask your agent to migrate

```text title="Prompt" wrap
Migrate my Railway project to InstaCloud, including the Postgres data. The repo is <owner/repo>. Follow the insta skill's migration runbook, and stop before moving DNS.
```

Your agent follows the migration runbook in the `insta` skill: it adds one compute service per Railway service, wires the database credential, deploys your repo, moves the data, and checks that it landed. It will ask you to approve the actions that touch production.

One thing is worth knowing, because it is the reason the runbook exists. Nothing on Railway can still be writing when the data moves, and Railway has no maintenance mode, so scale the service to zero in the dashboard yourself, along with every worker and cron service. Once the new database has writes of its own, going back to Railway quietly loses them.

{/* screenshot: console, project canvas with a compute service and a postgres service deployed */}

### 4. Move the domain

```text title="Prompt" wrap
Attach <your-domain> to the compute service and give me the DNS records to publish.
```

Publish the records at your provider, then ask your agent to check the domain. Keep the Railway project frozen, and do not delete it, until the old records have aged out of resolver caches.

### 5. Branch the database

Railway gives you environments. InstaCloud branches the database with them, so a branch is a real Postgres of its own rather than a second copy you keep in sync by hand.

```text title="Prompt" wrap
Create a branch called <name> and deploy the current code to it.
```

There is nothing to migrate for this one. For most people it is the reason to move.

## Prefer to run it yourself?

Everything your agent does is a command you can run. The [CLI reference](/reference/cli/overview) has all of them, and these are the ones this migration turns on:

```bash
insta services add compute app
insta services add postgres db
insta secrets bind DATABASE_URL postgres/db --to compute/app
insta compute connect-repo <owner/repo> app
insta secrets set <NAME>                       # value read from stdin
```

The database move is the one worth seeing in full. Scale Railway to zero first, including workers and cron services, so nothing is still writing:

```bash
pg_dump --no-owner --no-privileges "$RAILWAY_DATABASE_URL" \
  | grep -v -E '^SET transaction_timeout' \
  | psql -v ON_ERROR_STOP=1 "$(insta db url --group db)"

insta compute restart app
```

The `grep` drops one setting that Railway's Postgres writes and InstaCloud's does not recognise.

If you had a volume, attach one and redeploy before you copy the files in. It mounts at `/data`, and only on the deploy after you attach it.

```bash
insta compute volume app --size 10
insta compute restart app
```

## Workers and cron services

A Railway worker becomes a second compute service. Give it a port to listen on and leave always-on enabled, because a suspended worker has no traffic to wake it.

Railway cron services have no direct equivalent. Use `pg_cron`, which InstaCloud's Postgres ships, or run a scheduler inside an always-on service.
