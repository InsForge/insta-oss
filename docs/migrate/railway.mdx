Railway and InstaCloud think about deployments the same way, so the concepts map almost one to one. This guide takes you from a running Railway project to the same app on InstaCloud, with its data. Your coding agent does most of it.

InstaCloud offers:

- **Postgres with real branching.** Give a feature, or an agent task, its own database and its own compute, then merge the structure back.
- **Built for coding agents.** A CLI and an MCP server your agent drives directly, with an approval gate on the actions that matter.
- **Flexible deployments.** A GitHub repo with no Dockerfile needed, your own Dockerfile, or an image from any registry.
- **Managed services alongside.** Postgres, Redis, MySQL, MongoDB, and object storage in one project.
- **Real support.** An active community on [Discord](https://discord.com/invite/MPxwj5xVvW).

## Migration steps

We will migrate [Railway's own Django template](https://github.com/railwayapp-templates/django), a Python service with a Postgres database. Its `railway.json` says how it was built:

```json
{
  "build":  { "builder": "RAILPACK" },
  "deploy": { "startCommand": "python manage.py migrate && gunicorn mysite.wsgi" }
}
```

| On Railway | On InstaCloud |
|---|---|
| Service | a **compute** service |
| Railway Postgres | a **postgres** service |
| Variables | project secrets |
| A `${{Postgres.DATABASE_URL}}` reference | a binding |
| Volume | `insta compute volume`, mounted at `/data` |

**One code change first.** InstaCloud hands Postgres to your app as a single `DATABASE_URL`. This template reads the five `PG*` variables Railway injects instead, so point it at the DSN before you start. In Django that is `dj-database-url`, and most other stacks take a DSN directly.

### 1. Set up your coding agent

```bash
npx -y insta@latest setup agent
```

That installs the `insta` CLI, the `insta` skill, and the MCP server for every coding agent on this machine. The skill is what knows how a Railway project maps onto services here.

### 2. Create a project

```bash
insta project create mysite
```

Or click **Create Project** in the [console](https://console.instacloud.com). A new project starts empty.

{/* screenshot: console, Create Project */}

### 3. Ask your agent to migrate

Create a Railway project token first, under **Project Settings → Tokens**. Railway's CLI picks a project interactively otherwise, and your agent cannot answer a picker.

```text title="Prompt" wrap
Migrate my Railway service mysite and its Postgres data to InstaCloud. The repo is railwayapp-templates/django, and my Railway project token is in RAILWAY_TOKEN. Follow the insta skill's migration runbook, and stop before moving DNS.
```

Your agent reads the project, provisions the services it maps onto, binds the database credential, deploys the repo, moves the data, and checks that it landed. It will ask you to approve the actions that touch production.

Two things it will hand back to you, because Railway has no command for either. **Scale the service to zero** in the dashboard when your agent says to: Railway has no maintenance mode, and every worker and cron service needs the same treatment. And if you have a **volume**, download it while the service is still running, because Railway refuses to read a volume whose service is stopped.

One thing is worth knowing, because it is the reason the runbook exists. Nothing on Railway can still be writing when the data moves. Once the new database has writes of its own, going back to Railway quietly loses them.

{/* screenshot: console, project with a compute service and a postgres service deployed */}

### 4. Move the domain

```text title="Prompt" wrap
Attach <your-domain> to the compute service and give me the DNS records to publish.
```

Publish the records at your DNS provider, then ask your agent to check the domain. Keep the Railway project frozen, and do not delete it, until the old records have aged out of resolver caches.

### 5. Branch the database

A branch gets its own Postgres and its own compute, created by one command. A schema change, a destructive test, or a second agent working in parallel therefore cannot reach your production data, which is what makes it safe to hand an agent a migration in the first place. It is the closest thing here to a Railway environment, except that an agent makes one per task rather than you duplicating one in the dashboard.

```text title="Prompt" wrap
Create a branch called <name> and deploy the current code to it.
```

Schema moves forward through migration files, not by merging databases. `insta branch merge` creates the services a branch added and nothing else crosses over, so keep every schema change in a migration file and it replays on the branch, then on main.

## Workers and cron services

A Railway worker becomes a second compute service. Give it a port to listen on and leave always-on enabled, because a suspended worker has no traffic to wake it.

Railway cron services have no direct equivalent. Use `pg_cron`, which InstaCloud's Postgres ships, or run a scheduler inside an always-on service.

And that is it. Everything your agent ran is a command you can run yourself, and the [CLI reference](/reference/cli/overview) has all of them. Stuck anywhere? Come to [Discord](https://discord.com/invite/MPxwj5xVvW).
