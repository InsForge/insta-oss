---
title: "Migrate from Heroku"
description: "Move a Heroku app — dynos, config vars, and Heroku Postgres — onto InstaCloud."
---

Heroku maps onto InstaCloud cleanly. A `web:` process becomes a **compute** service, Heroku Postgres becomes a **postgres** service, and config vars become project secrets bound into the app's environment. Everything below runs from the Heroku CLI plus the `insta` CLI — no dashboard required.

## TL;DR

```bash
npx -y insta@latest setup agent --create        # install the CLI, link this dir to a new project
insta services add compute app
insta services add postgres db
insta secrets bind DATABASE_URL postgres/db --to compute/app
insta build . --port <listen-port>              # offline check: will this build?
insta deploy . --port <listen-port>             # needs a Dockerfile — alternatives below
# copy config vars (see step 4), then the data (step 5)
insta compute restart app
insta compute set-domain app <your-domain>
```

<Steps>
  <Step title="Take stock of the Heroku app" titleSize="h2">
    You need three things from Heroku: its processes, its config vars, and its addons.

    ```bash
    heroku ps --app <heroku-app>          # which process types exist (web, worker, …)
    heroku config --json --app <heroku-app> > heroku-config.json
    heroku addons --app <heroku-app>      # Postgres? Redis? Scheduler?
    ```

    Your `Procfile` names the same processes. A `web:` line becomes one compute service. A `worker:` line needs [an extra step](#workers-and-scheduled-jobs).

    <Note>
      `heroku-config.json` holds live credentials. Delete it when you are done, and keep it out of git.
    </Note>
  </Step>

  <Step title="Create the project and its services" titleSize="h2">
    ```bash
    npx -y insta@latest setup agent --create
    insta services add compute app
    insta services add postgres db          # add redis/mysql/mongodb/storage to match your addons
    ```

    A new project starts empty — nothing is provisioned until you ask for it.
  </Step>

  <Step title="Bind the database, then get the app running" titleSize="h2">
    Nothing is auto-injected into compute — bind each credential the app needs first.

    ```bash
    insta secrets bind DATABASE_URL postgres/db --to compute/app
    ```

    Then get the code running. Check locally first — this is offline and deploys nothing:

    ```bash
    insta build . --port <listen-port>
    ```

    Only a `deployable` verdict means `insta deploy .` will build it. A Heroku app usually has no Dockerfile — buildpacks did that job — so expect the Dockerfile check to come back `needs-attention` — the report prints the install and start commands it detected, and those are what you base one on. The `insta` skill carries per-framework Dockerfile templates.

    <Warning>
      Do **not** save the Dockerfile that `insta build --explain` prints as your `Dockerfile`. It is not standalone: it `COPY`s `.nixpacks/` support files your directory does not have.
    </Warning>

    With a Dockerfile in place:

    ```bash
    insta deploy . --port <listen-port>
    ```

    **Two alternatives if you would rather not write one.** Connect the app's GitHub repo in the [console](https://console.instacloud.com) — that build runs server-side and detects the runtime for you, the same job buildpacks were doing, and a public repo needs no GitHub App installation. Since `insta` 0.0.64 this is a CLI lane too — `insta compute connect-repo <owner/repo> app` attaches the repo to the compute service you already made and builds its Dockerfile, or detects the runtime with nixpacks when there is none. Or `insta deploy --image <registry/image> --port <n>` if you already publish an image.

    Do this before the config vars are in: the first deploy is what makes the binding live, and it gives you a URL to check.

    <Warning>
      `--port` must equal the port your server actually listens on. `PORT` is injected for you, so an app that reads `$PORT` is fine; a hardcoded port boots "successfully" and refuses every request.
    </Warning>
  </Step>

  <Step title="Copy the config vars" titleSize="h2">
    Two groups get skipped. **Heroku's own** (`HEROKU_*`, `DYNO`, `PORT`) are supplied by the platform. **Anything you bound** in the previous step — `DATABASE_URL`, `REDIS_URL`, the `AWS_*` storage credentials — comes from the service that minted it, and InstaCloud refuses a plain secret that collides with a binding, so copying those in makes the import fail rather than overwrite anything.

    ```bash
    jq -r 'keys[]' heroku-config.json \
      | grep -vE '^(HEROKU_|DYNO$|PORT$|DATABASE_URL$|REDIS_URL$|MYSQL_URL$|MONGODB_URL$|BUCKET_NAME$|AWS_)' \
      | while read -r k; do
          jq -j --arg k "$k" '.[$k]' heroku-config.json | insta secrets set "$k"
        done
    ```

    `insta secrets set` takes one variable per call and reads the value from stdin, which keeps secrets out of your shell history.

    <Warning>
      **This loop trims.** `insta secrets set` strips leading and trailing whitespace from a value read on **stdin**, so trailing newlines are harmless (`jq -j` above is belt-and-braces) — but a value whose edge whitespace is meaningful is silently corrupted. Passing it as an argument instead preserves it byte-for-byte: `insta secrets set NAME "  padded  "`, at the cost of the value appearing in your shell history. An **empty** value is refused either way. Scan the export for both cases first and handle them by hand.
    </Warning>
  </Step>

  <Step title="Move the data" titleSize="h2">
    Put Heroku in maintenance mode first, and stop its workers — a read-only web tier with a live worker is still writing.

    ```bash
    heroku maintenance:on --app <heroku-app>
    heroku ps:scale worker=0 --app <heroku-app>      # if you have workers

    set -o pipefail
    pg_dump --no-owner --no-privileges "$(heroku config:get DATABASE_URL --app <heroku-app>)" \
      | psql -v ON_ERROR_STOP=1 "$(insta db url)"
    ```

    <Warning>
      Both flags are load-bearing. `psql` continues past errors by default, and a shell pipeline reports only its last command's status — without `ON_ERROR_STOP=1` and `pipefail`, a half-restored database exits `0` and looks like success.
    </Warning>

    Then check it: row counts on your largest tables, and the newest row in anything append-only.
  </Step>

  <Step title="Point the app at the new database" titleSize="h2">
    ```bash
    insta compute restart app
    ```

    A restart re-runs the image already recorded — no rebuild — and re-resolves the environment. Until it happens, the running machine still holds the env it was deployed with.

    Confirm the app reads **and writes** the new database before moving on.
  </Step>

  <Step title="Move the domain" titleSize="h2">
    ```bash
    insta compute set-domain app <your-domain>
    insta compute check-domain app
    ```

    Once traffic is served from InstaCloud and you have soaked for a while, turn Heroku off.
  </Step>
</Steps>

## Workers and scheduled jobs

**`worker:` processes.** Add a second compute service and deploy your worker image to it. Give the worker a port and let it listen — one line is enough (`require('net').createServer().listen(process.env.PORT)`) — and leave always-on enabled, because a suspended worker has no incoming traffic to wake it.

**Heroku Scheduler.** There is no direct equivalent. Run an in-process scheduler inside your web service (node-cron, APScheduler, whenever). Keep that service always-on, and note that replicas each run every tick — two replicas means every job fires twice.

## What this guide does not cover

Rolling back after the new database has taken writes, verifying values survived the copy byte for byte, moving objects out of an external S3 bucket, and zero-downtime cutovers via logical replication.

Your coding agent has the full runbook — the ordered cutover with its pass conditions and rollback boundary — in the `insta` skill installed by `setup agent`. Ask it to migrate the app and it will follow that procedure rather than this summary.
