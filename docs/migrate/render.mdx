---
title: "Migrate from Render"
description: "Move a Render web service, its environment, and its Postgres onto InstaCloud."
---

A Render web service becomes an InstaCloud **compute** service, and Render Postgres becomes a **postgres** service. Environment variables become project secrets that you bind into the app.

## TL;DR

```bash
npx -y insta@latest setup agent --create
insta services add compute app
insta services add postgres db
insta secrets bind DATABASE_URL postgres/db --to compute/app
insta compute connect-repo <owner/repo> app
insta compute set-domain <your-domain> --group app
```

<Steps>
  <Step title="1. Inventory the Render service" titleSize="h2">
    The Render CLI is interactive by default. Add `-o json --confirm` to script it.

    ```bash
    render services -o json --confirm     # services and databases in one call
    ```

    If your repo has a `render.yaml`, read it as well. Anything set with `generateValue` or `sync: false` has no copy outside Render, so collect those values now.
  </Step>

  <Step title="2. Create the project and services" titleSize="h2">
    ```bash
    npx -y insta@latest setup agent --create
    insta services add compute app
    insta services add postgres db        # plus redis/mysql/mongodb/storage to match
    ```
  </Step>

  <Step title="3. Bind the database and deploy" titleSize="h2">
    Bind the credentials your app needs, then point InstaCloud at your repo.

    ```bash
    insta secrets bind DATABASE_URL postgres/db --to compute/app
    insta compute connect-repo <owner/repo> app
    ```

    `connect-repo` builds on the server and detects your runtime with nixpacks, so you do not need a Dockerfile. Add `--root-dir` for a monorepo. If you already publish an image, use `insta deploy --image <ref> --port <n>` instead.

    Then copy the remaining environment variables. Skip `RENDER_*` and `PORT`, which the platform supplies, and skip anything you bound above.

    ```bash
    insta secrets set <NAME>              # value read from stdin
    ```
  </Step>

  <Step title="4. Move the data" titleSize="h2">
    Scale the Render web service to zero first, along with any worker and cron job, so nothing is still writing.

    ```bash
    pg_dump --no-owner --no-privileges "$RENDER_DATABASE_URL" \
      | grep -v -E '^SET transaction_timeout' \
      | psql -v ON_ERROR_STOP=1 "$(insta db url --group db)"
    ```

    The `grep` drops one setting that Render's Postgres writes and InstaCloud's does not recognise. Then compare a few row counts before you carry on.

    ```bash
    psql "$(insta db url --group db)" -c \
      "select relname, n_live_tup from pg_stat_user_tables order by n_live_tup desc limit 5"
    ```
  </Step>

  <Step title="5. Restart, then move the domain" titleSize="h2">
    A restart re-resolves the environment, so the app picks up its new database.

    ```bash
    insta compute restart app
    insta compute set-domain <your-domain> --group app
    insta compute check-domain <your-domain> --group app
    ```

    `set-domain` returns the DNS records to publish at your provider. Publish them, then run `check-domain` again. Keep Render frozen until the old records age out.

    <Warning>
      If you stopped the InstaCloud service at any point, `insta compute start` on its own brings the machine back with its old environment, and the app keeps writing to the old database. Run `restart` after `start`.
    </Warning>
  </Step>
</Steps>

## Workers and cron jobs

A Render background worker becomes a second compute service. Give it a port to listen on, and leave always-on enabled, because a suspended worker has no traffic to wake it.

Render cron jobs have no direct equivalent. Use `pg_cron`, which InstaCloud's Postgres ships, or run a scheduler inside an always-on service.
