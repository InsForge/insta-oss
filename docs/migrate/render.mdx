This guide takes you from a running Render service to the same app running on InstaCloud, with its data. You will spend most of it telling your coding agent what to do.

InstaCloud offers:

- **Postgres with real branching.** Give a feature, or an agent task, its own database and its own compute, then merge the structure back.
- **Built for coding agents.** A CLI and an MCP server your agent drives directly, with an approval gate on the actions that matter.
- **Flexible deployments.** A GitHub repo with no Dockerfile needed, your own Dockerfile, or an image from any registry.
- **Managed services alongside.** Postgres, Redis, MySQL, MongoDB, and object storage in one project.
- **Real support.** An active community on [Discord](https://discord.com/invite/MPxwj5xVvW).

## Migration steps

We will migrate [Render's own Django example](https://github.com/render-examples/django), a Python web service with a Postgres database. Substitute your own names as you go.

Here is its `render.yaml`:

```yaml
databases:
  - name: mysitedb

services:
  - type: web
    name: mysite
    runtime: python
    buildCommand: "./build.sh"
    startCommand: "python -m gunicorn mysite.asgi:application -k uvicorn.workers.UvicornWorker"
    envVars:
      - key: DATABASE_URL
        fromDatabase:
          name: mysitedb
          property: connectionString
      - key: SECRET_KEY
        generateValue: true
      - key: WEB_CONCURRENCY
        value: 4
```

| On Render | On InstaCloud |
|---|---|
| Web service | a **compute** service |
| Render Postgres | a **postgres** service |
| Environment variables | project secrets |
| `DATABASE_URL` via `fromDatabase` | a binding, not a copied string |

Workers and cron jobs are at the end of the page.

### 1. Set up your coding agent

```bash
npx -y insta@latest setup agent --create
```

That installs the `insta` CLI, creates a project, links this directory to it, and registers the `insta` skill with every coding agent on this machine. The skill is what carries the migration runbook.

You can also create the project in the [console](https://console.instacloud.com) and connect an agent from its Quick Start page.

{/* screenshot: console, project Quick Start page with the connect-agent one-liner */}

### 2. Collect what your agent cannot reach

Two things do not exist anywhere your agent can read:

- **Values Render invented.** `SECRET_KEY` above is `generateValue: true`, so Render made it up and nothing outside Render has a copy. Anything marked `sync: false` is the same story, typed by a human and never in the file. Copy them off your service's **Environment** page now. For `SECRET_KEY` in particular, changing it logs every Django session out, so bring the existing value rather than generating a new one.
- **Your DNS provider login**, for the last step.

### 3. Ask your agent to migrate

```text title="Prompt" wrap
Migrate my Render service mysite and its Postgres database mysitedb to InstaCloud. The repo is render-examples/django. Follow the insta skill's migration runbook, and stop before moving DNS.
```

Your agent follows the migration runbook in the `insta` skill: it adds the services, wires the database credential, deploys your repo, moves the data, and checks that it landed. It will ask you to approve the actions that touch production.

One thing is worth knowing, because it is the reason the runbook exists. Your agent stops Render from taking writes before InstaCloud starts taking them. Once the new database has writes of its own, going back to Render quietly loses them.

{/* screenshot: console, project canvas with a compute service and a postgres service deployed */}

### 4. Move the domain

```text title="Prompt" wrap
Attach <your-domain> to the compute service and give me the DNS records to publish.
```

Publish the records at your provider, then ask your agent to check the domain. Keep the Render service suspended, and do not delete it, until the old records have aged out of resolver caches.

### 5. Branch the database

Now that you are here, branch your database along with your code. Ask for a branch per feature, or per agent task, and each one gets its own Postgres and its own compute.

```text title="Prompt" wrap
Create a branch called <name> and deploy the current code to it.
```

There is nothing to migrate for this one. For most people it is the reason to move.

## Prefer to run it yourself?

Everything your agent does is a command you can run. The [CLI reference](/reference/cli/overview) has all of them, and these are the ones this migration turns on:

```bash
insta services add compute mysite
insta services add postgres mysitedb
insta secrets bind DATABASE_URL postgres/mysitedb --to compute/mysite
insta compute connect-repo render-examples/django mysite
insta secrets set SECRET_KEY                   # value read from stdin
insta secrets set WEB_CONCURRENCY 4
```

The database move is the one worth seeing in full. Scale Render to zero first, including workers and cron jobs, so nothing is still writing:

```bash
pg_dump --no-owner --no-privileges "$RENDER_DATABASE_URL" \
  | grep -v -E '^SET transaction_timeout' \
  | psql -v ON_ERROR_STOP=1 "$(insta db url --group mysitedb)"

insta compute restart mysite
```

The `grep` drops one setting that Render's Postgres writes and InstaCloud's does not recognise.

## Workers and cron jobs

A Render background worker becomes a second compute service. Give it a port to listen on and leave always-on enabled, because a suspended worker has no traffic to wake it.

Render cron jobs have no direct equivalent. Use `pg_cron`, which InstaCloud's Postgres ships, or run a scheduler inside an always-on service.
