This guide takes you from a running Render service to the same app on InstaCloud, with its data. Your coding agent does most of it.

InstaCloud offers:

- **Postgres with real branching.** Give a feature, or an agent task, its own database and its own compute, then merge the structure back.
- **Built for coding agents.** A CLI and an MCP server your agent drives directly, with an approval gate on the actions that matter.
- **Flexible deployments.** A GitHub repo with no Dockerfile needed, your own Dockerfile, or an image from any registry.
- **Managed services alongside.** Postgres, Redis, MySQL, MongoDB, and object storage in one project.
- **Real support.** An active community on [Discord](https://discord.com/invite/MPxwj5xVvW).

## Migration steps

We will migrate [Render's own Django example](https://github.com/render-examples/django), a Python web service with a Postgres database. Here is its `render.yaml`:

```yaml
databases:
  - name: mysitedb

services:
  - type: web
    name: mysite
    runtime: python
    buildCommand: "./build.sh"
    envVars:
      - key: DATABASE_URL
        fromDatabase:
          name: mysitedb
          property: connectionString
      - key: SECRET_KEY
        generateValue: true
      - key: WEB_CONCURRENCY
        value: 4
```

| On Render | On InstaCloud |
|---|---|
| Web service | a **compute** service |
| Render Postgres | a **postgres** service |
| Environment variables | project secrets |
| `DATABASE_URL` via `fromDatabase` | a binding, not a copied string |

### 1. Set up your coding agent

```bash
npx -y insta@latest setup agent
```

That installs the `insta` CLI, the `insta` skill, and the MCP server for every coding agent on this machine. The skill is what knows how to read a `render.yaml` and turn it into services.

### 2. Create a project

```bash
insta project create mysite
```

Or click **Create Project** in the [console](https://console.instacloud.com). A new project starts empty.

{/* screenshot: console, Create Project */}

### 3. Ask your agent to migrate

Get a Render API key first, under **Account Settings → API Keys** in the Render dashboard. Your agent needs it to read your environment variables, which the Render CLI has no command for.

```text title="Prompt" wrap
Migrate my Render service mysite and its Postgres database mysitedb to InstaCloud. The repo is render-examples/django, and my Render API key is in RENDER_API_KEY. Follow the insta skill's migration runbook, and stop before moving DNS.
```

Your agent reads your `render.yaml`, provisions the services it maps onto, binds the database credential, deploys the repo, moves the data, and checks that it landed. It will ask you to approve the actions that touch production.

One thing is worth knowing, because it is the reason the runbook exists. Your agent stops Render from taking writes before InstaCloud starts taking them. Once the new database has writes of its own, going back to Render quietly loses them.

{/* screenshot: console, project with a compute service and a postgres service deployed */}

### 4. Move the domain

```text title="Prompt" wrap
Attach <your-domain> to the compute service and give me the DNS records to publish.
```

Publish the records at your DNS provider, then ask your agent to check the domain. Keep the Render service suspended, and do not delete it, until the old records have aged out of resolver caches.

### 5. Branch the database

A branch gets its own Postgres and its own compute. A schema change, a destructive test, or a second agent working in parallel therefore cannot reach your production data, which is what makes it safe to hand an agent a migration in the first place. Render has the same idea in preview environments, tied to a pull request and configured through a Blueprint. Here it is one command, so an agent can take a branch for a task before any pull request exists.

```text title="Prompt" wrap
Create a branch called <name> and deploy the current code to it.
```

Schema moves forward through migration files, not by merging databases. `insta branch merge` creates the services a branch added and nothing else crosses over, so keep every schema change in a migration file and it replays on the branch, then on main.

## Workers and cron jobs

A Render background worker becomes a second compute service. Give it a port to listen on and leave always-on enabled, because a suspended worker has no traffic to wake it.

Render cron jobs have no direct equivalent. Use `pg_cron`, which InstaCloud's Postgres ships, or run a scheduler inside an always-on service.
