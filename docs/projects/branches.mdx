---
title: "Branches"
description: "A branch clones the database with data, the bucket, and every compute service."
---

A branch is a full, isolated clone of your environment. Every project starts on `main`; a branch forks from a parent and lives until you delete it. Use branches for staging, per-agent tasks, and per-pull-request environments.

## What gets cloned

| Piece | On the new branch |
| --- | --- |
| Postgres | Copy-on-write clone with the parent's data, own connection string |
| Storage | Copy-on-write fork of the bucket's objects |
| Compute | A clone of each app at its own URL, running the parent's image |
| Secrets | Copied, with service bindings remapped to the branch's services |
| Managed databases (`redis`/`mysql`/`mongodb`) | A fresh, empty instance — no data cloned |
| Compute `/data` volume | Same size, empty — no data inheritance |

<Note>
On self-hosted insta-oss, the database and bucket are full copies (dump-and-restore, object sync) rather than copy-on-write — same isolation, duplicated at clone time.
</Note>

## Creating and switching

```bash
insta branch create staging
insta branch switch staging
insta secrets
```

`create` forks from your current branch — choose the parent explicitly with `--from <branch>`. Creating does not switch you: `switch` rewrites the directory link (`.insta/project.json`), after which every command targets the branch. Rerun `insta secrets` to refresh `.env`.

## Branch URLs and credentials

Each branch's compute services get their own URLs, printed on deploy and listed by `insta manifest`. Credentials are per-branch: `insta db url` prints the branch's connection string, and the branch's copied bindings point at the branch's own services, so work done on a branch stays on that branch. The boundary is separation, not authorization: commands that accept `--branch` (`secrets`, `deploy`, `storage delete`, and others) reach any branch in both directions, governed by [policy](/governance/overview) — gate the actions that matter if agents can reach the project.

## Merging

```bash
insta branch merge staging --into main
```

Merging is structural and additive: a service that exists on the source but not the target is created there, empty — deploy to it afterwards. Data never merges — promoting data changes means running your migrations against the target and deploying. Existing services are skipped with a reason (`exists`, `cap`).

## Limits

- 10 branches per project.
- Names: lowercase letters, digits, and dashes, up to 39 characters, starting with a letter or digit.

## Deleting

```bash
insta branch delete staging
```

Tears down the branch's database, bucket fork, compute, and secrets. `branch.delete` is a [gated action](/reference/gated-actions) — put it behind approval if agents can reach the project.
